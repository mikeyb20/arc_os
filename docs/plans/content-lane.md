# Content lane — conventions for the pack pipeline blocks

Written by M3-00a (2026-11-11). Applies to M3-01, M3-03, M3-04 and M3-04b (work-blocks.md §4, §5), which turn
Kiwix ZIM files into installable knowledge packs on a Linux build host while the kernel lane works through M1.
Every content-lane spec lists this file under "Read first".

## The pipeline

```
sources.json (M3-01)
  → ZIM file ──zim_extract.py──→ article stream (.jsonl)        host only, Python      M3-03
  → packbuild build ──→ content/ + chunks/                       C, stack/, lane libs   M3-03
  → packbuild index ──→ fts/index.sqlite                         C (arcsearch)          M3-04
  → packbuild manifest ──→ manifest.json                         C                      M3-04
  → arcpkg build ──→ <name>-<version>.arcpkg                     C (arcpkg, M5-02)      M3-04
  → tiers.py ──→ tiers.json (which packs each storage tier gets) host only, Python      M3-04
  → vectors/<embedder>/ (M2-06's embedder)                       spec from M3-00        M3-04b
```

## Where the line between host-only and C is (decided by M3-00a)

- **Reading the source format is host-only Python.** `tools/content/zim_extract.py` opens the ZIM, walks the
  articles and turns their HTML into pack markup (`docs/formats/pack-v1.md`, "Document text"). ADR-0011 rules out
  parsing ZIM or HTML on arc_os, so this code never needs to run there; Python's `html.parser` (standard library)
  handles real-world HTML with far less code than C would. The ZIM itself is read with python-libzim (Kiwix's
  reader, host only, archived like every other outside source) unless Michael chooses an in-house reader
  (decision card, 2026-11-11).
- **Every step after extraction is C in `stack/`**, on the lane libraries (arcpack, arcsearch, arcjson, arcutil),
  linked with musl, and tested in lane L inside the syscall inventory (lane-l.md). Those steps already have their
  libraries: the pack writer (M3-02), the FTS builder (M3-06a), SHA-256 and durable writes (M5-02), the package
  reader (M5-02). Writing the rest in C keeps the pack rules (chunking, manifest, checksums, package layout) in one
  language next to the readers, and lets the same programs later run on arc_os: re-chunking or re-indexing a pack,
  adding vectors, or packaging a model (M5-05) without a Linux host. Nothing here plans that work; it only keeps
  it possible.
- The **article stream** (`docs/formats/article-stream.md`, written by M3-03) is the boundary: JSON Lines that any
  extractor can produce. A second source format later means a second extractor, not a second pipeline.
- `tools/content/` holds the host-only scripts (Python 3, run with `python3 -I`, standard library plus
  python-libzim). Their tests are host tests (`ctest -L host`), with fixtures generated by the test itself.
  `catalog.py` reads the Kiwix catalog (cloud sessions can't reach it, so the `catalog` GitHub job runs it and
  prints the table into its log); `budget.py` holds the tier budgets and the pack size estimate (M3-01).

## Keyword-only first, vectors later

- M3-03 and M3-04 build **keyword-only** packs: `provides: ["fts"]`. Search and reading work without the LLM
  (ADR-0015), so these packs are useful as soon as they install.
- Vectors need the embedder that M2-06 picks, so they come in **M3-04b**, specified by M3-00 after M2-06. It adds
  `vectors/<embedder>/` to each pack and publishes it as a new minor version (`2026.11.0` → `2026.11.1`): same
  article stream, same chunking options, so `content/` and `chunks/` are byte-identical and every chunk ID stays the
  same. `arcpkg` treats the same version as already installed, which is why vectors bump the version.
- **Chunk size is set for the embedder that isn't chosen yet:** `tokenizer: "words"` (runs of Unicode letters and
  digits), target 280 words, at most 360, overlap 40. At about 1.3 model tokens per English word that is ~360–470
  tokens, inside ADR-0011's 300–500 and under the 512-token limit common to small embedders. If M2-06 picks an
  embedder with a smaller limit, M3-00 says whether M3-04b rechunks (a new major version, new chunk IDs) or lets
  the embedder truncate.

## Where things live

- **Code** (extractor, `packbuild`, `arcpkg build`, `tiers.py`): this public repo.
- **Content lists** (`sources.json`, M3-01) and anything else about what Michael ships: the private content repo,
  or `/mnt/project-files/arc_os/content/` until it exists (knowledge-os.md §10: `arc_os` is public).
- **ZIM files and built packs**: on the build host, never in git or release assets (GitHub's 2 GiB asset limit, and
  they are content, not source). Each ZIM's SHA-256 goes in `sources.json` when it is downloaded, so a build names
  its exact input.
- **Build host**: Michael's laptop by default (work-blocks.md §6, "Before M3-03"), driven through a Remote Control
  session; `download.kiwix.org` is blocked from cloud sessions. CI and lane tests never download a ZIM: they build
  tiny fixtures (a generated ZIM for the extractor, a generated article stream for `packbuild`).

## Rules every content-lane block follows

- **Deterministic builds.** The same ZIM and options give byte-identical `content/` and `chunks/` (documents
  sorted by their ZIM path, fixed zstd level). The FTS index may differ in bytes but holds the same rows.
- **Streams, not dumps.** A ZIM is read entry by entry and never unpacked to disk; `packbuild` keeps one document
  in memory plus the path index (about 40 bytes per document).
- **Licence and source travel with the data**: from `sources.json` into every pack manifest and `.arcpkg`.
- **Package builders compress with a window of at most 8 MiB** (schemas/README.md). Pack files are already
  compressed, so `arcpkg build` uses a fast level for them.
- Measured sizes (text, chunks, strings, FTS, packages) go in the block's Notes and correct M3-01's estimates.
  They are content numbers, not CI budgets; CI budgets cover the programs (`packbuild_bytes`, RSS on a fixture).
